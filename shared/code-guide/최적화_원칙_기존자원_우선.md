# 최적화 원칙 — 기존 자원 우선

> 새 함수·hook·추상화를 만들기 전에 현재 자원으로 해결 가능한지 먼저 검증한다

#react #optimization #code-review #ag-grid

## 원칙

성능, reference 안정화, 상태 동기화 같은 최적화 요구가 생겼을 때 **새 abstraction부터 만들지 않는다.** 다음 순서를 지킨다.

1. **현재 상황 + 사용 중인 라이브러리의 기존 API/패턴**을 먼저 충분히 살펴본다
2. 기존 자원으로 해결 가능한 길이 있으면 그 쪽을 선택한다
3. 진짜 만에 하나 기존 자원으로 해결 불가능할 때만 새로 만든다

급하게 결론 내지 말고, **현재 상황을 충분히 고려한 후** 수정 방향을 정한다.

## Why — 왜 이 원칙이 중요한가

새 abstraction을 만드는 비용은 눈에 잘 안 보인다.

- 새 hook/유틸 → 명명·테스트·문서화·import 경로 늘어남
- 같은 일을 하는 두 방법 공존 → 코드 리뷰 시 "어느 쪽이 정석이지?" 혼란
- 라이브러리가 이미 제공하는 기능을 우회 → 라이브러리 업그레이드 시 깨질 위험
- 작성한 사람이 떠나면 "왜 이 헬퍼가 필요했지?" 라는 흔적만 남음

기존 자원을 충분히 살펴보면 새 코드 없이 끝나는 경우가 많다.

## Do — 실제 적용 체크리스트

reference 안정화·캐싱·상태 동기화 같은 최적화 요구를 만나면, **새 헬퍼 만들기 전에** 아래를 순서대로 확인한다.

| 체크 항목 | 확인 방법 |
|---|---|
| 라이브러리가 자체 store를 가지고 있나? | `gridRef.current.api.*`, `queryClient.getQueryData`, zustand `getState()` |
| 호출 시점에 라이브러리가 최신 값을 넘겨주나? | ag-grid `params.data`, react-hook-form `getValues()`, 이벤트 핸들러 인자 |
| 이미 stable한 reference가 있는데 못 쓰고 있는 게 아닌가? | zustand actions, useCallback으로 감싼 함수, ref.current |
| 클로저로 잡으려는 외부 state가 진짜 필요한가? | 인자/ref로 대체 가능한지 검토 |
| 단순 `useCallback(fn, [deps])`로 안 되는 진짜 이유가 있나? | deps가 불안정한 게 hook 구조 문제 때문이면 그걸 먼저 고친다 |

이 체크리스트를 통과한 뒤에도 답이 안 나오면 그때 새 hook/유틸을 만든다.

## 사례 — ag-grid editButtonAction reference 안정화

`/resp/pol` 같은 페이지에서 페이지네이션 클릭 시 사용자가 늘린 컬럼 width가 초기화되는 문제.

### 원인 진단

- `CommonGrid.tsx`의 `columnDefs` useMemo가 `editButtonAction` reference에 의존
- page에서 `editButtonAction = useMemo(..., [canUpdate, handleEditClick])`로 감쌌지만
- hook 측 `handleEditClick`이 `useCallback`이 아닌 일반 함수 → render마다 새 reference
- → page useMemo deps가 매번 무효화 → editButtonAction 새 reference → 컬럼 재구성

### 시도 1 — 새 헬퍼 도입 (잘못된 길)

ref 패턴으로 reference만 안정화하는 `useStableCallback` 헬퍼를 새로 만들고 6개 페이지에 적용.

```ts
// shared/hooks/useStableCallback.ts (불필요했음)
export const useStableCallback = (fn) => {
  const ref = useRef(fn);
  ref.current = fn;
  return useCallback((...args) => ref.current(...args), []);
};
```

```tsx
// page (불필요한 우회)
const stableHandleEditClick = useStableCallback(handleEditClick);
const editButtonAction = useMemo(
  () => (canUpdate ? stableHandleEditClick : undefined),
  [canUpdate, stableHandleEditClick],
);
```

### 시도 2 — 기존 자원 활용 (정석)

**ag-grid는 자체 store를 가진 라이브러리이고, 호출 시점에 `params.data`로 최신 rowNode.data를 넘겨준다.** 이 사실을 충분히 활용하지 않은 게 문제였음.

hook의 `handleEditClick`이 매 render 새 reference가 된 진짜 이유는 안에서 `items.find(...)`로 외부 state(React Query 결과)를 클로저로 잡아 lookup하기 때문이었음. 그런데 ag-grid가 넘기는 `row`는 이미 그 items 중 하나와 같은 reference. **find가 애초에 불필요했음.**

```ts
// hook — 기존 자원으로 해결
const handleEditClick = useCallback(
  (row: PolicyItem) => {
    openModal('policyDetailModal', { mode: 'edit', rowData: row });
    //                                                       ↑ ag-grid가 넘긴 그대로
  },
  [openModal],  // zustand action → 영구 stable
);
```

```tsx
// page — 헬퍼 없이 단순 useMemo
const editButtonAction = useMemo(
  () => (canUpdate ? handleEditClick : undefined),
  [canUpdate, handleEditClick],
);
```

### 비교

| | 시도 1 (헬퍼 도입) | 시도 2 (기존 자원) |
|---|---|---|
| 추가된 파일 | `useStableCallback.ts` 1개 | 없음 |
| 페이지마다 import 늘어남 | 1개 | 없음 |
| 외부 state 클로저 | 있음 (items.find) | 없음 |
| reference 안정화 메커니즘 | page 측 ref 우회 | hook이 useCallback으로 자체 안정 |
| 신규 개발자가 이해하는 데 필요한 지식 | "ref 패턴 + stale closure" | "useCallback 기본기" |

시도 2가 모든 면에서 우월. 시도 1의 `useStableCallback`은 도입 직후 다시 삭제됨.

## 따름원칙 — useCallback / useMemo도 추상화다

useCallback도 새 abstraction의 한 형태. **수신자가 reference를 보는 게 증명될 때만** 단다.

### 달아야 하는 경우

| 상황 | 이유 |
|---|---|
| `React.memo` 자식에 prop으로 넘김 | 자식이 reference 비교로 re-render 결정 |
| 다른 hook의 deps에 들어감 | reference가 deps 비교에 쓰임 |
| 라이브러리가 reference 기반 최적화를 함 | 예: ag-grid `editButtonAction` → `columnDefs` 재계산 |

### 안 달아도 되는 경우 (대부분)

| 상황 | 왜 무의미한가 |
|---|---|
| 일반 `<button onClick={fn}>` | DOM은 reference 비교 안 함 |
| hook 안에서 한 번 호출하고 끝 | 외부로 안 나가니 안정성 무의미 |
| 자식이 일반 컴포넌트(memo 안 됨) | 어차피 부모 render 시 자식도 같이 render |

### 숨은 비용

- render마다 deps 비교 (0은 아님)
- 캐시 메모리 보관
- deps 관리 부담 (빠뜨리면 stale closure, 과하면 매번 무효화)
- eslint-exhaustive-deps와의 끝없는 싸움
- 가독성 ↓ — 모든 함수가 `useCallback(...)` 옷을 입으면 본질이 안 보임

## 일반화 — 같은 패턴이 적용되는 다른 케이스

- **react-hook-form**: 폼 값을 클로저로 잡지 말고 `getValues()` / `watch()` 사용
- **react-query**: 외부에서 데이터가 필요하면 `queryClient.getQueryData(queryKey)` 직접 조회
- **zustand**: 컴포넌트 밖에서 store 읽기는 `useModalStore.getState()`
- **DOM 측정**: ref + `getBoundingClientRect()` 호출 시점 측정, state로 끌어올리지 않기

공통: **"클로저로 잡지 말고 호출 시점에 라이브러리에 직접 물어본다."**
